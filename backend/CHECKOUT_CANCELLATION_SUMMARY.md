# ملخص تنفيذ إلغاء Checkout واستعادة المخزون

## ما تم تنفيذه

- إضافة `POST /api/checkouts/<checkout_id>/cancel`:
  - يتطلب JWT، ويسمح للتاجر مالك عملية الشراء فقط.
  - يمنع إلغاء عملية مدفوعة، ويتعامل مع الإلغاء المكرر دون استعادة المخزون مرة أخرى.
  - يرفض الإلغاء عندما تكون حالة الدفع جارية أو مجهولة.
- استعادة كميات المنتجات من عناصر الطلبات المرتبطة بالـ checkout، وتحديث حالة المخزون، وإلغاء الطلبات المعلّقة ضمن معاملة PostgreSQL واحدة.
- استخدام أقفال للصفوف لتنسيق الإلغاء وبدء الدفع والـ webhook، ومنع استعادة المخزون مرتين.
- إضافة تسجيل محاولة الدفع قبل إرجاع بيانات التهيئة الخاصة بـ Moyasar.
- تحديث الـ webhook للتحقق من الدفع مباشرةً لدى Moyasar، والإبقاء على تحقق المبلغ والعملة وسلوك إشعارات الدفع المعتاد.
- تسجيل الدفع الناجح الذي يصل بعد الإلغاء أو الانتهاء في قائمة مراجعة مالية، دون إعادة فتح checkout أو إصدار استرداد تلقائي.
- إضافة عامل دوري لانتهاء عمليات الشراء الآمنة فقط، وتأجيل الحالات ذات الدفع غير المؤكد.
- إضافة مدة انتهاء قابلة للإعداد وترحيل قاعدة بيانات جديد.

## الملفات المضافة

- `backend/checkout_lifecycle.py` — قواعد إغلاق checkout واستعادة المخزون.
- `backend/expire_checkouts.py` — عامل الانتهاء وأداة عرض المدفوعات قيد المراجعة.
- `backend/migrations/008_checkout_lifecycle.sql` — أعمدة الحالات والطوابع الزمنية وجداول تتبع الدفع والتسوية.
- `backend/tests/test_checkout_lifecycle.py` — اختبارات دورة حياة checkout.
- `backend/README.md` — شرح استخدام المسارات والعامل والترحيل ومخاطر الدفع.

## خطوات النشر المطلوبة

1. خذ نسخة احتياطية واتبع آلية المشروع المعتادة لتطبيق `backend/migrations/008_checkout_lifecycle.sql` بعد الترحيلات السابقة.
2. اضبط `CHECKOUT_EXPIRATION_MINUTES` على عدد دقائق موجب؛ القيمة الافتراضية `30`.
3. جدْول تشغيل العامل من مجلد `backend` كل بضع دقائق:

   ```powershell
   python expire_checkouts.py
   ```

4. لمراجعة المدفوعات الناجحة التي وصلت بعد إغلاق checkout:

   ```powershell
   python expire_checkouts.py --reconciliations
   ```

5. راجع هذه الحالات يدوياً في Moyasar وسجّل التسوية المالية المناسبة. التطبيق لا ينفذ استردادات تلقائية.

## حدود مهمة لتكامل الدفع

- الواجهة الحالية تستخدم مسار الطلبات القديم `/api/orders` ولا تستخدم `/api/checkouts` أو Moyasar.
- يجب على أي عميل يستخدم checkout الجديد استدعاء `/api/checkouts/<id>/payment-attempts` قبل تهيئة الدفع، واستخدام `checkout_id` و`payment_attempt_id` الواردين في البيانات التعريفية.
- مسار محاولة الدفع يسجل المحاولة قبل تسليم بيانات التهيئة، لكنه لا ينشئ عملية الدفع لدى Moyasar من الخادم. الدفع الذي يبدأ من عميل يتجاوز هذا المسار لا يمكن رصده مسبقاً؛ لذلك لا يمكن ضمان سلامة تحرير مخزونه عند الإلغاء أو الانتهاء. يلزم إنشاء الدفع server-to-server أو آلية مكافئة تمنع المحاولات غير المسجلة.
- بعد تطبيق الترحيل، تبقى عمليات checkout الموجودة بحالة دفع `unknown`؛ لن يحرر العامل مخزونها تلقائياً، ويجب التحقق منها يدوياً قبل أي قرار.
